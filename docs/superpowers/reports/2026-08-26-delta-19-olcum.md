## 1 + 2. Renk: sözleşme yayında, VERİ yok

`POST /products` boş gövdeyle:

```
["…","En fazla 15 resim yüklenebilir","En az 3 resim yüklenmelidir","images must be an array",
 "…","Renk en fazla 80 karakter olabilir","Renk zorunludur","color must be a string","…"]
```

Aynı uca `{"colors":["red","black"], …}` gönderildiğinde **`Renk zorunludur` /
`color must be a string` hataları KAYBOLUYOR**. Yani yeni DTO'nun koşullu kuralı
(`color` yalnız `colors` boşken zorunlu) staging'de canlı — `colors[]` kabul ediliyor.

Ama katalog boş:

```
GET /products/attribute-groups →
  scale        | attrs=9
  material     | attrs=4
  vehicle_type | attrs=12
```

**`color` grubu yok.** Ana repodaki `dc00df45a feat(api): add a targeted seeder for
the colour attribute group` seed'i staging'de koşulmamış.

Filtrenin canlı olduğu, "bilinmeyen parametre yutuluyor" ihtimalinden ayrıştırıldı:

```
GET /products?limit=1            → total=44
GET /products?limit=1&color=red  → total=0     ← filtre UYGULANIYOR
GET /products?limit=1&zzzz=red   → total=44    ← bilinmeyen parametre yutuluyor
GET /products?limit=1&scale=1-18 → total=8     ← kıyas
```

Ürünler hâlâ serbest metin renk taşıyor: `{"color":"Mavi"}`, `attributes[]` içinde
renk yok.

**Karar:** Mobilde renk SEÇİCİSİ ve renk FİLTRESİ bu turda **yazılmıyor**. Seçenek
listesi `attribute-groups`'tan gelir; grup boşken yazılacak kod ölü dal olur — bu
tam olarak `relatedOrder`/`relatedTrade` turunda yapılan hata. Madde
**backend/ops'a devredildi**: staging + prod'da renk seed'i koşulmalı.

Bunun bugünkü kullanıcı etkisi: **mobilden açılan ilanlar web'in yeni renk
filtresinde çıkmaz.** Ancak web de aynı durumda — grup seed'lenene kadar filtre
web'de de 0 sonuç veriyor. Yani bu bir mobil/web ayrışması değil, ortak bir veri
borcu.

## 4. Misafir sipariş iptali — YAYINDA

```
POST /orders/guest/cancel  {}  → 400
{"message":["orderNumber must be a string","email must be an email"],"statusCode":400}
```

404 değil 400 → uç canlı. Kimlik doğrulama takip ucuyla aynı (sipariş no + e-posta).
Opsiyonel `reasonCode` (`OrderCancellationReason` enum) + `reason` (≤500 karakter).
Mobilde `app/order-track/` yalnız `guest/track` çağırıyor, iptal aksiyonu yok.

## 5. Sunucu hataları artık çeviriliyor — YAYINDA

```
POST /auth/login (hatalı) + accept-language: tr
  {"statusCode":401,"message":"Email veya şifre hatalı","i18nKey":"server.auth.invalidCredentials"}
POST /auth/login (hatalı) + accept-language: en
  {"statusCode":401,"message":"Invalid email or password","i18nKey":"server.auth.invalidCredentials"}
GET /products/<yok> + accept-language: en
  {"statusCode":404,"message":"Product not found","i18nKey":"server.product.notFound"}
```

**Sınır (ölçüldü):** class-validator DTO mesajları çeviriye girmiyor — dekoratörde
sabit Türkçe metin. `accept-language: en` ile de `"Başlık en az 5 karakter olmalıdır"`
dönüyor. Yani alan doğrulama hataları her dilde Türkçe.

Mobil `i18nKey`'i zaten okuyor (`src/lib/api/authFailureKind.ts`, `requestId.ts`)
ama `Accept-Language` **göndermiyor** → `settings/language`'dan İngilizce seçen
kullanıcı Türkçe sunucu hatası görüyor.

## 6. `tradeFeeDiscountAmount` — YAYINDA, ama DTO'nun söylediği yerde değil

DTO'da `TradeResponseDto` üzerinde duruyor gibi görünüyor; gerçekte **nakit ödeme
satırında**:

```
GET /trades?limit=5 → .trades[0].cashPayments[]:
{"id":"d3ac9b47…","payerId":"…","amount":0,"tradeFeeAmount":200,
 "tradeFeeDiscountAmount":0,"shippingAmount":200,"commission":0,
 "totalAmount":400,"status":"pending"}
```

`cashPayment` (tekil) da aynı alanı taşıyor. Örnek veride değer `0` — kampanya
uygulanmış bir takas bulunamadı, yani **alan var, dolu örnek yok**. Mobil
`app/trade/[id]/_lib/types.ts`'teki `TradeCashPayment` bu alanı taşımıyor.

## 7. Kupon `target` — ÖLÇÜLEMEDİ

```
POST /discounts/validate {"code":"YOKBOYLEKOD","cartTotal":1000} → 200
{"isValid":false,"error":"Kupon kodu bulunamadı"}
GET /discounts?limit=5 → {"items":[],"total":0,…}
```

Hesapta kupon yok, geçerli bir kod bulunamadı → başarı gövdesindeki `target` /
`budgetRemaining` / `maxDiscountAmount` **doğrulanamadı**. Tip yazılmıyor.

**Yan ölçüm — açık madde teyidi:** kupon reddi hâlâ `{isValid:false, error:"<düz
Türkçe metin>"}`. `i18nKey` YOK. `PARITE_KALAN_ISLER.md`'deki "kupon reddi 400'ünde
yapısal alan yok" maddesi **geçerliliğini koruyor** — `i18nMessage` göçü bu yolu
kapsamamış (reddi exception olarak fırlatmıyor, 200 ile dönüyor).
